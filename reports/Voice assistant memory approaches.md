# Voice assistant memory approaches

The projects inspected use **recent conversation history and durable memory as separate layers**. The first carries the exact dialogue needed for follow-up questions; the second carries selected facts, preferences or summaries into later sessions. Implementations range from a file containing a compact summary to databases and dedicated retrieval services. For WhisperStack, the strongest practical starting point is bounded session history, followed by editable facts and summaries in SQLite. A memory service becomes useful when selective recall or automatic fact maintenance warrants its additional components. This is a recommendation from inspected implementations, not an accepted project decision or evidence that one architecture dominates the community.

The user's comparison is with the first WhisperStack build's runtime Markdown memory. Changing that storage format alone would not decide which facts to remember, when to update them, or what to include in each request. Those policies distinguish the implementations below. Sources were inspected on October 26, 2026, often on moving branches; none of these projects was installed or benchmarked for this research.

| Project | What its implementation does | Useful lesson for WhisperStack |
|---|---|---|
| **LiveKit Agents** | Maintains ordered application-side chat context, supports loading user information at session start and retrieving database context during a turn, and provides history truncation. ([Chat context](https://docs.livekit.io/agents/logic/chat-context/)) | Session context can be implemented in the existing backend without adopting a new voice framework. |
| **Pipecat** | Uses shared context plus user/assistant aggregators around the voice pipeline. Optional background summarization replaces older context while keeping recent turns and protecting incomplete tool sequences. ([Context management](https://docs.pipecat.ai/pipecat/learn/context-management), [Summarization](https://docs.pipecat.ai/pipecat/fundamentals/context-summarization)) | Keep recent dialogue exact; summarize older material when it becomes necessary. |
| **Xiaozhi ESP32 server** | Includes conversation messages separately from injected memory. Its local provider persists an LLM-generated JSON summary in YAML; another provider explicitly adds and searches memories through Mem0. ([Dialogue](https://raw.githubusercontent.com/xinnan-tech/xiaozhi-esp32-server/main/main/xiaozhi-server/core/utils/dialogue.py), [Local memory](https://raw.githubusercontent.com/xinnan-tech/xiaozhi-esp32-server/main/main/xiaozhi-server/core/providers/memory/mem_local_short/mem_local_short.py), [Mem0 adapter](https://raw.githubusercontent.com/xinnan-tech/xiaozhi-esp32-server/main/main/xiaozhi-server/core/providers/memory/mem0ai/mem0ai.py)) | A close ESP32 comparison supports both simple summary storage and a retrieval service. |
| **Home Assistant** | Keeps chat logs by conversation ID. Session cleanup uses a five-minute idle threshold with periodic cleanup; active turns refresh the timestamp. ([Chat logs](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/conversation/chat_log.py), [Sessions](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/helpers/chat_session.py)) | Define when a conversation continues, expires or explicitly resets. Session history and a lasting personal profile serve different purposes. |
| **Alexsay smart speaker** | Uses SQLite and loads recent conversation material alongside durable facts. Its memory module generates a short session summary and structured fact additions, updates and removals after a conversation; new facts link to their source conversation. ([Memory implementation](https://github.com/andreasbros/alexsay/blob/main/api/src/memory.ts)) | SQL plus bounded dialogue, summaries and editable facts is a concrete voice-project architecture. |

Voice adds an important bookkeeping constraint. **A generated answer is not necessarily a heard answer.** Pipecat commits the spoken portion when playback is interrupted, and LiveKit truncates assistant history to speech heard before interruption. WhisperStack currently offers mute rather than true barge-in, but a future memory design should distinguish generated text, delivered audio and playback state. Otherwise a follow-up can refer to information the listener never received. This is design guidance, not authorization to add realtime microphone behavior. ([Pipecat interruptions](https://docs.pipecat.ai/pipecat/fundamentals/interruptions), [LiveKit turns](https://docs.livekit.io/agents/logic/turns/))

Dedicated memory systems automate more of the durable layer. **Mem0** provides fact extraction, embeddings, retrieval and update/delete operations; its defaults introduce inference and storage components beyond an ordinary chat request. Pipecat publishes an example combining session context with Mem0 and ElevenLabs TTS, demonstrating that persistent memory can be added alongside an existing speech pipeline. Self-hosted storage can still use external inference providers. ([Mem0 quickstart](https://docs.mem0.ai/open-source/python-quickstart), [Pipecat example](https://github.com/pipecat-ai/pipecat/blob/main/examples/rag/rag-mem0.py))

**Graphiti** models entities, relationships and facts changing over time, using a graph backend plus inference and embedding clients. That fits richer relationship queries but adds infrastructure for a small personal assistant. **Letta** offers a stateful agent platform and a separate experimental memory SDK; its maintainers recommend batching messages or processing evicted turns to reduce additional calls. These are viable alternatives when their features are needed, with no established speed advantage for our Haiku/ElevenLabs loop. ([Graphiti](https://github.com/getzep/graphiti), [Letta memory SDK](https://github.com/letta-ai/ai-memory-sdk))

The recommendation is to begin with a session identifier, a bounded list of exact exchanges, and clear new-conversation behavior. Later, a separate durable store can hold facts with timestamps and source turns, plus a compact summary when warranted. Memory consolidation should run after the spoken response or at session end where feasible, so it does not become a prerequisite for the next answer. Recent exact turns still provide immediate follow-up context while longer-term processing catches up. Summarization and extraction accuracy would need tests on our own examples.

Before implementation, agree on whether sessions survive restarts, when they expire, and whether personal facts are saved automatically or only through an explicit request. Include review, correction and forgetting from the beginning. Real project discussions report stale context and uncertainty about updating changed preferences, but these are user reports rather than controlled comparisons. ([Home Assistant discussion](https://github.com/orgs/home-assistant/discussions/4568), [Xiaozhi memory question](https://github.com/xinnan-tech/xiaozhi-esp32-server/issues/3334)) WhisperStack currently has a single-turn voice loop and optional client-supplied text history; this research changes neither retention nor runtime behavior.
