# Face renderer

The FACE OLED (the second SSD1306 panel on I²C bus 1) now has two
selectable renderers, controlled at build time by the `CONFIG_FACE_RENDERER`
Kconfig choice. Default is `ROBO_EYES`.

## The Kconfig flag

`firmware/main/Kconfig.projbuild`:

```
choice FACE_RENDERER
    prompt "Face renderer for the FACE OLED ..."
    default FACE_RENDERER_ROBO_EYES

    config FACE_RENDERER_CAT_FACE
        bool "Cat-face (legacy pre-rendered framebuffers)"

    config FACE_RENDERER_ROBO_EYES
        bool "FluxGarage RoboEyes port (GPL-3.0)"
endchoice
```

Selecting `CAT_FACE` plays the pre-rendered animation tables from
`firmware/main/cat_face.h` (auto-generated by `tests/oled_dump_c.py`
from `tests/oled_animate.py`). Selecting `ROBO_EYES` runs the
FluxGarage RoboEyes port at `firmware/components/robo_eyes/`.

Both renderers stay in tree; the unused branch is gated out at
compile time via `#if CONFIG_FACE_RENDERER_*`. Switching is a
two-step menuconfig + rebuild — there's no runtime switch.

## The port

The upstream is a header-only C++ template class
(`template<typename AdafruitDisplay> class RoboEyes`) that calls
Adafruit_GFX drawing primitives on an arbitrary display. Pulling
Arduino-ESP32 + Adafruit_GFX into this codebase would be heavyweight;
instead, the port:

- Translates the class to a single static `robo_eyes_state_t` in C
  (we have exactly one face panel; no instance pluralism needed).
- Re-implements the three GFX primitives the upstream actually
  uses — `fill_rect`, `fill_round_rect`, `fill_triangle` — over a
  1024-byte in-memory framebuffer in SSD1306 page-byte order
  (8 pages × 128 bytes, bit 0 of each byte = top pixel). This is
  the same layout the existing `oled_face_draw_bitmap()` driver
  expects, so the face task just `memcpy`s the buffer in.
- Preserves the upstream's behavior verbatim:
  - Eye geometry defaults (36×36, border radius 8, gap 10).
  - Per-frame `(cur + next) / 2` tween — same easing rate.
  - Auto-blinker random interval = `interval_s + random(variation_s)`.
  - Idle-mode random target inside the screen-X/Y envelope.
  - Mood overlay shapes (TIRED top triangles drooping outward,
    ANGRY top triangles pointing inward, HAPPY lower-half carved
    away by a BG-color rounded rect, DEFAULT no overlay).
  - Confused / laugh one-shot animations via 500 ms of h/v flicker.
- Skips upstream's `sweat` drop animation — the v3 plan doesn't
  exercise a "stressed" mood and the float-driven drop logic is
  weight without a use case. Re-add later if "stressed" enters the
  state machine.
- Adds one read-only accessor not in the upstream:
  `robo_eyes_get_eye_x_angle()`. Returns the currently-displayed eye
  horizontal direction as a float in degrees. Used by the follower
  task that drives the SG90 servo behind the eyes; see
  [`notes/motion-character.md`](motion-character.md) for the
  architecture. No state-mutating extensions remain — the library is
  otherwise byte-faithful to upstream.

During the port, a one-shot Python reimplementation of the
drawing primitives + final-frame draw logic was run inline to
emit a 4×3 preview sheet (4 moods × 3 positions) into a scratch
PNG. It confirmed the port produces the canonical RoboEyes
silhouettes — rounded squares (DEFAULT), asymmetric drooping
(TIRED), inward-pointed angry-cat (ANGRY), arc-eyed smile
(HAPPY) — plus smooth horizontal pan to W / center / E. The PNG
is intentionally not in the tree (it's a transient sanity
check); the inline script lives in the session transcript only.
**Caveat:** this validates the *algorithm*, not the *C code*.
The Python uses PIL's raster, not the SSD1306 page-byte
framebuffer the C path writes into. Page-byte convention was
verified separately by reading `firmware/main/oled.c`'s
`oled_draw_text` (which writes `glyph[i]` directly into
`fb[line*OLED_W + col]`, bit 0 = top of page) and matching it
to the port's `(y/8)*screen_w + x` byte index and
`1 << (y & 7)` bit mask. Convention matches; `cat_face.h`'s
generator (`tests/oled_dump_c.py`) uses the same convention.

## State → mood mapping

`firmware/main/main.c`'s `face_task` (RoboEyes branch) maps the
existing application state machine to RoboEyes moods:

| `app_state_t`        | Mood       | Idle mode | Notes |
|----------------------|------------|-----------|-------|
| `APP_STATE_BOOT`     | DEFAULT    | off       | Eyes wake from closed → open over ~120 ms. |
| `APP_STATE_IDLE`     | DEFAULT    | **on**    | Ambient: autoblinker @ ~3 s + variation 3 s, random gaze wander @ 1 s + variation 3 s. SG90 head follows the eyes when `CONFIG_GAZE_COUPLING_DEMO` is set. |
| `APP_STATE_LISTENING`| DEFAULT    | off       | Idle wander frozen so any future external override (wake-event reaction) can drive the gaze without competition. |
| `APP_STATE_THINKING` | TIRED      | off       | Drooping lids read as "processing". |
| `APP_STATE_SPEAKING` | HAPPY      | off       | Lifted lower lids — engaged smile. |

The fourth upstream mood, **ANGRY**, is intentionally not mapped
yet. It's reserved for a future error / timeout / cancelled state
(e.g. `APP_STATE_ERROR` if/when that gets added). The reservation
is cheap — `robo_eyes_set_mood(ROBO_EYES_MOOD_ANGRY)` already works,
nothing's hardcoded — so adding the wiring later is a single
`switch` arm.

Why these choices specifically:

- **IDLE = DEFAULT + idle mode + autoblinker**: gives the face
  ambient life without overcommitting to an expression. Mirrors
  how a person looks when nothing's happening — neutral face,
  occasional blinks, eyes drift around.
- **LISTENING = DEFAULT + idle mode OFF**: the wake-toward-sound
  reaction wants to drive the gaze externally; leaving idle mode
  on would compete with the externally-set position and the eyes
  would visibly resist tracking. Same reason `servo_set_posture`
  switches off the SG90 drift task when entering LISTENING.
- **THINKING = TIRED**: the heavy-lidded shape reads as
  contemplative on this tiny canvas. Alternative considered:
  ANGRY (focused), but the asymmetric inward triangles read as
  "annoyed" more than "focused" once you're looking at them.
- **SPEAKING = HAPPY**: the arc-eyed smile is universally legible
  and matches the existing cat-face's `^_^` SPEAKING look so
  switching renderers doesn't visually invert the meaning of
  "speaking."

## Gaze coupling — head follows eyes

The OLED + SG90 coupling architecture isn't a face-renderer concern;
it's a follower task that reads the library's eye state. See
[`notes/motion-character.md`](motion-character.md) for the full
design, tunable knobs, and the rationale for why the head follows
the eyes (rather than the other way around — which was an earlier
attempt that didn't work).

Read path from the library side: `robo_eyes_get_eye_x_angle()`
returns the eye's currently-displayed horizontal angle in degrees
(derived from `eyeLx` relative to the screen-X envelope center).
That's the only API a follower needs from this side. No setter, no
overrides — the library generates motion autonomously via its
autoblinker + idle-mode defaults.

The earlier exploration of an external-driver architecture
(`set_position_continuous`, `set_position_x_continuous`,
`set_idle_axes`) was reverted on 2026-05-11 in favor of this simpler
read-only contract. Git history preserves the prior approach if
you want to compare; the short version is that driving the face
from a synthetic intention model under-performed the library's
own organic idle-wander tuning by a substantial margin.

## Things deliberately NOT done tonight

- **Sweat drops** — upstream feature, float-heavy, no use case.
- **Cyclops mode wiring** — supported by the port via
  `robo_eyes_set_cyclops(true)` but not exposed at the state level.
- **`anim_confused` / `anim_laugh` triggers** — supported but not
  bound to any state transition. Easy to add when a recognizable
  trigger exists (e.g. confused on speech-rec failure).
- **Re-tuning eye geometry for the round display** — `ROUND_240`
  is mentioned in `tests/oled_animate.py` as a future layout
  preset; the RoboEyes port respects whatever screen dimensions
  `robo_eyes_begin()` is called with, so this becomes a single-call
  change on hardware day. (The earlier note here about pending
  `idf.py build` verification is now obsolete — the firmware has
  been built, flashed, and visually confirmed on real v1 hardware
  during the same session.)
